## WinForms docs panel (F1) — review and plan

### Goal

Port the Avalonia `DocsPanel` to WinForms with the same features. It is a plain `UserControl`, so
the client app chooses how to show it (dock, form, tab, docking library). The WinForms sample shows
it in a fixed panel to the right of the editor, trialled first in the BasicDemo only.

Design reference: `docs/log/2026-10-19-log.md` (the Avalonia design, which
anticipated this port). Everything not drawing was put in the shared core on purpose.

### What the review found

**Already shared, and reused as-is (no changes expected)** — `CDS.CSharpScript2/Documentation/`:
- `DocPage`, `DocRun` / `DocRunKind`, `DocTarget`, `DocNamedItem`, `DocOverload`, `DocMemberGroup`:
  the UI-neutral page model.
- `DocsPanelController`: the Closed/Following/Browsing state machine, history, loading state,
  superseded-request handling, and a `Changed` event. Its awaits deliberately have no
  `ConfigureAwait(false)` so `Changed` fires on the UI thread; WinForms has a
  `SynchronizationContext`, so that holds there too.
- `IDocPageSource`, implemented over `EditorManager.GetDocPageAsync` (position and target).
- `HelpRequestedEventArgs(int Position)` is already in core.
- Unit tests for the controller and pages already exist (`UT_DocsPanelController`, `UT_DocPages`).

**Avalonia-only — the parts that need a WinForms equivalent:**

| Avalonia piece | What it does | WinForms equivalent |
|---|---|---|
| `DocsPanel` (UserControl) | Header (Back, Forward, state chip, "Follow caret (F1)", close), scrolling body, 300 ms caret debounce, F1 and Escape handling, `ShowRequested` / `CloseRequested`, `Editor` property, `Close()` | New `DocsPanel : UserControl` in the Scintilla editor project |
| `DocPageRenderer` | Turns a `DocPage` into TextBlocks, inline links, code runs, overload highlight, member groups | New renderer writing into a read-only `RichTextBox` |
| `DocLink` | Clickable inline text, hand cursor, underline on hover | Link spans recorded while rendering, then hit-tested from mouse events |
| `DocsPanelPalette` | Colours derived from the editor theme (bg, fg, dim, link, code, chip pairs) | Same derivation as `System.Drawing.Color` |
| `EditorDocPageSource` | Makes the manager's document current before each request, then calls the manager | Same job; see "Editor hooks" below |
| `AvaloniaScriptEditor.Help.cs` | `HelpRequested`, `CaretMoved`, `CaretOffset`, `RequestHelp()`, F1 handler, `EnsureManagerDocumentCurrentAsync` | New members on `ScintillaScriptEditor` |

**Scintilla editor today:** F1 is handled in `OnKeyDown` (`ScintillaScriptEditor.cs` ~line 1496). It
calls `manager.GetAPIInfo(pos)` and shows the provisional `FormAPIInfo` window. There is no
`HelpRequested`, no `CaretMoved`, no theme-changed event (`Theme` is a settable property only), and
`Manager` is only reachable through `API.Manager`.

### Design decisions (proposed — see "Needs Jon" for the ones that are his)

1. **Rendering: a read-only `RichTextBox`.** Appending styled runs is simple (font, colour,
   underline per run), it wraps and scrolls natively, it is already a dependency of this repo (the
   output panel), and it works on net48 and net10. Links are drawn as coloured/underlined ranges and
   recorded as `(start, length, DocTarget)`; click and hover use `GetCharIndexFromPosition`. The
   overload highlight uses `SelectionBackColor`. The alternatives (owner-drawn control, stacked
   Labels) cost far more for little gain. No WebView2 (anti-goal in the spec).
2. **No flicker (anti-goal in the spec).** Rebuild only when the controller's `Changed` fires with a
   different page; suspend redraw (`WM_SETREDRAW`) around a rebuild; keep the scroll position when
   the same page re-renders (theme, state) and reset to the top for a new page — exactly as the
   Avalonia panel does with `_renderedPage`.
3. **The panel never shows or hides itself.** Same events as Avalonia: `ShowRequested`,
   `CloseRequested`; plus `Close()` for hosts that hide it by other means. `panel.Editor = editor`
   connects it.
4. **Theme.** Add `ThemeChanged` to `ScintillaScriptEditor` and have the connected panel follow the
   editor's `Theme`, so the host does not have to set it twice. (BasicDemo currently sets
   `Theme` on the editor and the output panel separately.) The panel also gets its own settable
   `Theme` for use without an editor.
5. **Editor hooks.** On `ScintillaScriptEditor`: `HelpRequested` event, `CaretMoved` event (from
   Scintilla `UpdateUI` when the selection changed), `CaretOffset`, `RequestHelp()`, and an
   internal way to bring the manager's document level with what is on screen before a page request
   (the WinForms analysis is debounced by `timerChangeMonitor`, same problem the Avalonia
   `EnsureManagerDocumentCurrentAsync` solves).
6. **F1 behaviour in the Scintilla editor.** Raise `HelpRequested`. If nothing is subscribed, keep
   today's `FormAPIInfo` behaviour so existing hosts are unchanged. (Avalonia spec: "F1 in the
   Scintilla editor keeps opening `FormAPIInfo` until the WinForms port".)
7. **Keys.** F1 and Escape are caught in the panel via `ProcessCmdKey`, so they work wherever focus is
   inside it (RichTextBox, buttons). Set `Handled` on the WinForms `HelpRequested` event so the OS
   help message does not fire as well.
8. **Colours.** The light/dark derivation in `DocsPanelPalette` is pure `System.Drawing.Color` maths
   on `EditorTheme`. Rather than copy ~15 constants, move it to core as a small shared type that both
   palettes use, so the two panels cannot drift apart. Optional first step (see plan).

### Things to check / risks

- **Position units.** Scintilla positions are byte offsets in UTF-8 while Roslyn wants character
  offsets. The existing F1 code passes `scintilla.CurrentPosition` straight to `GetAPIInfo`, so find
  out whether the editor already converts (a helper), or whether non-ASCII text above the caret
  breaks it today. Must be settled before `CaretOffset` is exposed publicly.
- **net48.** `ScintillaEditor` multi-targets `net48` and `net10.0-windows`. Anything new has to build
  on both (no `Index`/`Range`, check BCL overloads). Build both after each step.
- **Editor file is large** (about 2,100 lines, with state-version and disposal guards around every
  async path). Hook changes need the same guards (`_editorStateVersion`, `CanAccessEditor`).
- **RichTextBox quirks:** selection highlight and caret in a read-only box, mouse-wheel focus,
  per-run font changes resetting line height, DPI scaling. Spike this first.
- **Testing.** Controller logic is already tested headlessly. The WinForms view needs in-process STA
  tests (the `UITests` project has `StaThreadRunner`; check whether the panel can be tested there
  without FlaUI) plus a BasicDemo test that F1 shows the panel.
- **Packaging.** The panel is public API in a packed assembly: XML-doc everything, no default
  parameters, one public type per file, and add a short section to `CDS.CSharpScript2.ScintillaEditor/readme.md`.

## Step 2b proposal: splitting `ScintillaScriptEditor.cs` (needs Jon's OK before any move)

Today the file is 2,113 lines in one class. It has clear regions already (the `// ── X ──` banners),
so the lowest-risk approach is the one `AvaloniaScriptEditor` already uses: **partial-class files by
concern, as pure moves with no behaviour change**, then pull genuinely separable logic out into helper
classes only where it can stand on its own.

|---|---|---|
| Fields, constants, construction, IScriptEditor members (1–420) | `ScintillaScriptEditor.cs` (stays, ~350) | The core: state, lifetime, public surface |
| Theming + `ApplyTheme` (170–190, 313–420) | `ScintillaScriptEditor.Theme.cs` | `ThemeChanged` already hooks here |
| Analysis cycle: timers, syntactic and live passes (423–655) | `ScintillaScriptEditor.Analysis.cs` | Holds the version counters; keep their comment |
| Diagnostics, classification, folding, gutter markers (656–984) | `ScintillaScriptEditor.Diagnostics.cs` and `.Folding.cs` | Two files; folding is self-contained |
| Highlight API (985–1048) | `ScintillaScriptEditor.Highlight.cs` | Small |
| Scintilla event handlers (1049–1304) | stay with their feature where obvious, else `.Events.cs` | Needs care: handlers are wired in the Designer by name |
| Code completion (1305–1565) | `ScintillaScriptEditor.Completion.cs` | |
| Line commenting (1566–1701) | `ScintillaScriptEditor.Commenting.cs` | Candidate for a helper (below) |
| Call tips (1702–2018) | `ScintillaScriptEditor.CallTips.cs` | `CallTipSession` is already its own class |

| F1 / caret / theme-changed hooks | `ScintillaScriptEditor.Help.cs` (done) | |

**Second stage — helper classes (only after the moves are in and green):**
- *Comment toggling:* the text logic (which lines, add or remove `//`) is separable from Scintilla; a
  small `LineCommenter` working on strings/line lists could be unit-tested without a control.
- *Fold application:* converting `FoldSpan`s into Scintilla fold levels and collapsed-line save/restore,

- *Classification painting* (mapping classification spans to Scintilla styles) similarly.
Each of these needs a look at how entangled it is with `scintilla` before deciding; I would not commit
to them up front.

**How I would do it:** one concern per step, each step a pure move, then `dotnet build` (both targets)
and `dotnet run --project UITests` before the next. No renames, no reformatting, no logic changes in the
same diff. Expected result: the main file drops from ~2,100 to ~350 lines and no file is over ~350.

**Question for Jon:** is partial-class-by-concern the right first level, or do you want helper classes
